# eda-bridge-mcp

MCP server bridging the three deterministic EDA workhorses — **Vivado**
(synthesis / timing / utilization), **Icarus Verilog** (functional simulation),
and **Verilator + Verible** (lint) — behind a single tool surface for Claude
Code / Codex CLI / OpenCode.

## Overview

No LLM calls are made here: `eda-bridge-mcp` is a pure subprocess gateway
with structured error parsing. Hosts discover five tools:

| Tool | Backed by | Purpose |
| --- | --- | --- |
| `run_lint` | verilator, verible-verilog-lint | Parallel static lint, ~12 ms/file |
| `run_synthesis` | vivado -mode batch | Out-of-context synth → timing + util reports |
| `run_simulation` | iverilog + vvp | Compile + run a testbench, capture stdout/VCD |
| `get_timing_report` | pure Python | Re-parse `timing*.rpt` in a project dir |
| `classify_errors` | pure Python | Map Vivado error codes to semantic categories |

All subprocess, scratch-path, and tool-lookup concerns route through
[`vibe4fpga-platform`](../../shared/platform/) — no `/tmp`, no bare
`shutil.which`, no raw `asyncio.create_subprocess_exec` call remains.

## Install

```bash
uv tool install eda-bridge-mcp                 # PATH entry "eda-bridge-mcp"
```

Developers working inside the monorepo use path-deps instead:

```bash
cd packages/mcp-servers/eda-bridge-mcp
uv sync --all-extras
```

## Configure

### Claude Code — `%USERPROFILE%\.claude.json`

```json
{
  "mcpServers": {
    "eda-bridge": {
      "command": "eda-bridge-mcp",
      "env": { "VIVADO_ROOT": "C:\\Xilinx\\Vivado\\2024.2" }
    }
  }
}
```

### Codex CLI — `%USERPROFILE%\.codex\config.toml`

```toml
[mcp_servers.eda-bridge]
command = "eda-bridge-mcp"
env = { VIVADO_ROOT = "C:\\Xilinx\\Vivado\\2024.2" }
```

### OpenCode — `%APPDATA%\opencode\config.json`

```json
{
  "mcp": {
    "eda-bridge": {
      "type":    "stdio",
      "command": ["eda-bridge-mcp"],
      "env":     { "VIVADO_ROOT": "C:\\Xilinx\\Vivado\\2024.2" }
    }
  }
}
```

Host snippets are regenerated by `tools/gen-skills/generate.py` — never
hand-edit the files under `configs/`.

## Tools

### `run_lint(project_path, files)`
Runs `verilator --lint-only` and `verible-verilog-lint` in parallel, merges
findings, and returns `{findings, error_count, warning_count, score_penalty}`.
If either tool is missing the other still runs; an `info` finding records the
gap.

### `run_synthesis(project_path, files, top_module, part="xc7a35tcpg236-1")`
Writes a fresh `run.tcl` into `project_path` (or a new scratch dir when
`project_path` is empty), runs `vivado -mode batch`, then parses the emitted
`timing.rpt` and `util.rpt`. Returns success flag, categorised errors, timing,
utilization, and the work dir for downstream tools.

### `run_simulation(project_path, testbench, source_files, simulator="icarus", vcd_output=None)`
`iverilog -g2012` compiles the sources + testbench into a scratch `.vvp`
(cross-platform, not `/tmp`), then `vvp` executes it. Returns stdout tail,
stderr tail, and the VCD path (if the testbench writes one).

### `get_timing_report(project_path)`
Walks `project_path` for the most recent `timing*.rpt` and returns
`{wns, tns}`.

### `classify_errors(raw_stdout)`
Pure-Python mapper: raw Vivado stdout → `[{code, category, suggestion}, ...]`.
Unknown errors are preserved as `{raw: "..."}`.

## Environment

| Var | Required for | Default |
| --- | --- | --- |
| `VIVADO_ROOT` | Vivado install hint (preferred) | — |
| `VIVADO_PATH` | Legacy alias for the above | — |

Icarus Verilog (`iverilog`, `vvp`), Verilator, and `verible-verilog-lint` are
discovered via `PATH` only. `vibe4fpga-platform.find_tool` handles the
Windows `.exe` + PATHEXT fallback automatically.

## Windows notes

* **No `/tmp`.** Scratch files live under the per-process
  `vibe4fpga_files_*` directory allocated by `vibe4fpga-platform` and are
  removed on process exit.
* **Long paths.** Vivado project / work directories deeper than 240 chars are
  auto-prefixed with `\\?\` by `platform.proc.run`. Enable
  `LongPathsEnabled=1` in Windows group policy for the Vivado build tree
  itself — Vivado's own tooling is not long-path aware.
* **UTF-8 console.** `PYTHONIOENCODING=utf-8` + `PYTHONUTF8=1` are pinned in
  the child env so Chinese / Japanese Windows hosts (default GBK/SJIS
  console) read Vivado stderr cleanly.
* **`VIVADO_ROOT` over `VIVADO_PATH`.** Either the install root (e.g.
  `C:\Xilinx\Vivado\2024.2`) or the `bin` dir (e.g.
  `C:\Xilinx\Vivado\2024.2\bin`) may be supplied — the resolver probes for
  a child `bin` directory.
* **Icarus on Windows.** Install via `scoop install iverilog` or the upstream
  MSI — both put `iverilog.exe` and `vvp.exe` on PATH.
* **Verilator on Windows.** Requires WSL or MSYS2; `find_tool` will honour
  whichever binary is first on PATH.

## Troubleshooting

* `vivado not found. Set VIVADO_ROOT ...` — neither `VIVADO_ROOT` /
  `VIVADO_PATH` nor PATH contains the Vivado binary. Set `VIVADO_ROOT` in
  the host config env block or prepend `<install>/bin` to PATH.
* `run_simulation` returns `{"error": "iverilog not found in PATH"}` —
  install Icarus (`brew install icarus-verilog`, `scoop install iverilog`,
  or apt).
* `run_lint` findings include an `info` severity record — that's just the
  corresponding linter missing from PATH; add it or ignore.
* Every `run_*` tool call produces a new scratch directory under the OS
  tempdir. It is auto-cleaned on process exit; to inspect, pass an explicit
  `project_path` to `run_synthesis`.
* `iverilog timed out after 120s` / `vvp timed out after 300s` — the
  testbench is likely in an infinite loop; inspect `source_files` for a
  missing `$finish`.
