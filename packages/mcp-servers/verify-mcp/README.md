# verify-mcp

MCP server for FPGA verification — testbench generation and multi-stage
scoring. Absorbs the `testbench_gen` and `verification` skills from the
retired monolithic `packages/skills/` package.

## Overview

Two LLM-backed tools, both reached over stdio MCP:

| Tool                 | Input model                | What it does                                                            |
| -------------------- | -------------------------- | ----------------------------------------------------------------------- |
| `generate_testbench` | `GenerateTestbenchInput`   | Synthesise a self-checking SystemVerilog testbench for the given RTL.   |
| `score_verification` | `ScoreVerificationInput`   | Parse lint/sim/formal/synth reports, run a spec compliance LLM check, score, and emit a Markdown narrative report. |

LLM calls flow through the shared
[`vibe4fpga-llm-client`](../../shared/llm-client/) adapter library, so any
backend key from its registry (`claude`, `gpt-4o`, `deepseek`, `gemini`,
`ollama`, `rtlcoder`, ...) works without code changes. Pure-logic scoring in
`verification.scorer` runs offline and is the backbone of the score breakdown
(deductions documented inline in `scorer.py`).

## Install

```bash
uv tool install vibe4fpga-verify-mcp                  # PATH entry "verify-mcp"
```

Developers working inside the monorepo use path-deps instead:

```bash
cd packages/mcp-servers/verify-mcp
uv sync --all-extras
```

## Configure

### Claude Code — `%USERPROFILE%\.claude.json`

```json
{
  "mcpServers": {
    "verify": {
      "command": "verify-mcp",
      "env": { "ANTHROPIC_API_KEY": "${env:ANTHROPIC_API_KEY}" }
    }
  }
}
```

### Codex CLI — `%USERPROFILE%\.codex\config.toml`

```toml
[mcp_servers.verify]
command = "verify-mcp"
```

### OpenCode — `%APPDATA%\opencode\config.json`

```json
{ "mcp": { "verify": { "type": "stdio", "command": ["verify-mcp"] } } }
```

Host snippets are regenerated by `tools/gen-skills/generate.py` — never
hand-edit the generated files.

## Tools

### `generate_testbench` (`GenerateTestbenchInput`)

| Field       | Type               | Default      | Notes                                              |
| ----------- | ------------------ | ------------ | -------------------------------------------------- |
| `rtl_code`  | `str`              | — (required) | The Verilog/SystemVerilog module under test.       |
| `spec`      | `str \| None`      | `None`       | Plain-English behaviour description.               |
| `coverage`  | `list[str] \| None`| `None`       | Named coverage goals woven into the LLM prompt.    |
| `simulator` | `str`              | `"iverilog"` | Target sim: `iverilog` / `verilator` / `xsim`.     |
| `model`     | `str \| None`      | `None`       | LLM model key (see llm-client registry).           |

Returns `{testbench_code, coverage_points, assertion_count, simulator,
warnings, summary}`.

### `score_verification` (`ScoreVerificationInput`)

| Field           | Type          | Default      | Notes                                                       |
| --------------- | ------------- | ------------ | ----------------------------------------------------------- |
| `rtl_code`      | `str`         | — (required) | RTL source; fed to the LLM spec-compliance check (stage 5). |
| `spec`          | `str \| None` | `None`       | When supplied, stage 5 runs.                                 |
| `sim_log`       | `str \| None` | `None`       | Raw simulator log.                                          |
| `lint_report`   | `str \| None` | `None`       | Verilator / Icarus / SpyGlass lint text.                    |
| `formal_report` | `str \| None` | `None`       | SymbiYosys (`sby`) report.                                  |
| `synth_report`  | `str \| None` | `None`       | Synthesis + timing summary (WNS extracted deterministically).|
| `model`         | `str \| None` | `None`       | LLM model key for narrative + spec check.                   |

Returns `{stages, score, verdict, overall_verdict, breakdown, notes,
report_md}`. Verdict thresholds: **PASS ≥ 85**, **REVIEW 60–84**, **FAIL < 60**.

## Environment

| Var                 | Required for                       | Default                  |
| ------------------- | ---------------------------------- | ------------------------ |
| `VIBE4FPGA_LLM`     | picking default backend            | `claude`                 |
| `ANTHROPIC_API_KEY` | `VIBE4FPGA_LLM=claude` (default)   | —                        |
| `OPENAI_API_KEY`    | OpenAI / DeepSeek backends         | —                        |
| `GEMINI_API_KEY`    | Gemini backend                     | —                        |
| `OLLAMA_BASE_URL`   | Ollama / RTLCoder backends         | `http://localhost:11434` |

See [`vibe4fpga-llm-client` README](../../shared/llm-client/README.md) for the
full backend table.

## Windows notes

* **No `/tmp`.** `verify-mcp` consumes caller-supplied report strings, so it
  never writes scratch files itself. Any tool chain that does should go
  through [`vibe4fpga-platform`](../../shared/platform/) (`scratch_file`,
  `scratch_dir`, `run`).
* **Long paths / UTF-8 console.** Irrelevant for this MCP (no subprocess),
  but if you chain it with `eda-bridge-mcp` to produce the input reports,
  those callers must set `PYTHONUTF8=1` and enable `LongPathsEnabled=1` so
  the reports aren't truncated or mangled before reaching `score_verification`.
* **PowerShell here-strings.** When feeding multi-line RTL via PowerShell,
  use `@' ... '@` to preserve backtick-quoted backticks in `` `timescale ``.

## Troubleshooting

* `AuthError: ANTHROPIC_API_KEY is not set` — the default
  `VIBE4FPGA_LLM=claude` requires the key. Set it in the host config or
  switch to `VIBE4FPGA_LLM=ollama` for offline operation.
* `generate_testbench` warnings mention missing `` `timescale `` — the LLM
  dropped the pragma. Re-run with a lower `temperature` in the skill source
  or retry; the warning does not fail the tool call.
* `score_verification` returns a `REVIEW` verdict you disagree with — inspect
  `notes[]`; each deduction is tagged with its stage and numeric hit so you
  can see whether a lint warning, a spec DECLARED clause, or a negative WNS
  pushed you below 85.
* `Simulation: inconclusive (no PASS/FAIL markers)` — your `sim_log` lacks
  the strings the heuristic looks for (`PASS`, `FAIL`, `$error`, `$fatal`,
  `Test PASSED/FAILED`). Post-process the log or inject explicit print
  statements into the testbench.
